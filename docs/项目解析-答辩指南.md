# AI 学生信息管理系统 —— 项目解析与答辩指南（大白话版）

> 这份文档用**最直白的话**把项目讲清楚：它是什么、怎么做的、牛在哪里。
> 哪怕完全没写过代码的人（小白），看完也能大致明白我们做了什么。

## 一、一句话介绍

**这是一个给高校用的"一站式"教务网站**：学生在上面选课、查成绩、问 AI 助手；老师在上面录成绩、发通知；教务秘书（教秘）在上面管账号、审成绩、看统计。三类人共用同一套数据，配上**实时通知**和**AI 学业助手**。

> 大白话：把教务处、老师、学生平时靠纸和口口相传干的事，全搬到网页上，还能**实时提醒**、**自动分析**。
> 打个比方：以前学校发成绩要靠班长一个个转告，现在系统"叮"一声直接推到你手机（网页）上。

## 二、解决什么问题

| 现实里的麻烦 | 我们系统的办法 |
|---|---|
| 选课靠人工登记，容易超员、信息不透明 | 在线选课中心：名额实时显示、**多人同时抢也绝不超卖**、时间冲突自动提醒 |
| 成绩靠 Excel 传来传去，流程乱、说不清 | 完整流程：**老师录入 → 提交 → 教秘审核 → 发布**，每一步都有记录、谁都改不了别人的环节 |
| 调课、出成绩靠人传话，经常收不到 | **实时通知**：在线秒收，不在线一上线就补发 |
| 学生看不懂成绩、不知道选什么课 | **AI 助手**：查自己成绩、做学业分析、推荐适合的课 |
| 数据散落各处，领导看不到全局 | **统计看板**：专业分布、分数段、热门课程等图表一眼看清 |

## 三、三种角色，各看各的

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│   学生 STUDENT │   │   教师 TEACHER │   │ 教秘 ADMIN   │
│  选课/查成绩   │   │  管课程/录成绩  │   │  管账号/审成绩 │
│  收通知/AI助手 │   │  发通知/看统计  │   │  发通知/看统计 │
└──────────────┘   └──────────────┘   └──────────────┘
         └──────────────┬──────────────┘
                 一套数据库 + 一套后端 + 一套前端
```

- **学生**：登录后选课、看课表、查成绩（只能看**已发布**的）、收实时通知、问 AI。
- **教师**：建课程、给**自己的**课程录成绩（支持 Excel 批量导入）、给自己的学生发通知、看自己课程的成绩统计。
- **教秘（管理员）**：管所有账号、审核并发布成绩、监控选课、给任意学生发通知、看全校统计。

> 关键点：**谁的权限都别想越界**。后端每个接口都会验身份、验角色——学生查不到别人的成绩，老师改不了别人的课程。
> 打个比方：就像门禁卡，学生卡只能开自己宿舍的门，老师卡只能开自己办公室的门，教秘卡能开所有门。

## 四、技术栈"大白话"解释

| 技术 | 是什么 | 在我们项目里干嘛 | 打个比方 |
|---|---|---|---|
| **Vue 3 + TypeScript** | 写网页界面的框架 + 带类型检查的语言 | 所有页面（选课、成绩、统计…）都是它画的 | 盖房子的砖和水泥 |
| **Element Plus** | 现成的漂亮 UI 组件库 | 表格、弹窗、表单不用从零写 | 装修用的成品家具 |
| **ECharts** | 图表库 | 统计页的柱状图、饼图 | 画图工具 |
| **Pinia** | 前端状态管理 | 登录状态、未读数等全局数据统一管 | 前台的总台账 |
| **Spring Boot 2.7** | Java 后端框架（主程序） | 提供所有接口、处理业务规则 | 餐厅后厨，所有菜都从这出 |
| **MyBatis-Plus** | 操作数据库的框架 | 不用手写一堆 SQL，用对象方式查库 | 仓库管理员的扫码枪 |
| **MySQL 8** | 关系型数据库（存数据的地方） | 存学生、课程、成绩、通知等**所有核心数据** | 大仓库 + 分类账本 |
| **Redis** | 内存数据库（快但存不久） | 登录防爆破计数、限流、选课缓存等**临时状态** | 前台桌上的便利贴，写得快、撕得快 |
| **WebSocket** | 双向实时连接 | **服务端主动把消息推给学生**（通知"实时"的关键） | 对讲机，后台喊一声前台立刻听到 |
| **FastAPI + LangGraph** | Python 后端 + AI 编排框架 | 独立的 AI 服务：判断意图→查资料→生成回答 | AI 专用的分诊台 + 流水线 |
| **DeepSeek API** | 大语言模型（在线服务） | AI 对话的"大脑" | 雇来的专家，按次付费 |
| **ChromaDB + BM25** | 向量库 + 关键词检索 | 让 AI 先"查课程资料"再回答，不瞎编 | 资料室 + 目录检索 |
| **Tavily** | 联网搜索引擎 API | 「自由问答」时让 AI 查真实网页资料，回答标注来源 | 请个"查资料的实习生"，按次付费 |
| **JWT + BCrypt** | 登录令牌 + 密码加密 | 登录后发"出入证"，密码加密存储 | 出入证 + 把密码绞成肉馅存起来 |
| **EasyExcel** | Excel 读写库 | 成绩/账号的批量导入导出 | 批量盖章机 |

## 五、架构分析（答辩深度讲解）

### 5.1 系统总览图

```
                 ┌─────────────────────────────┐
                 │       前端 Vue3 (5173)       │
                 │ 页面 + 图表 + WebSocket 客户端 │
                 └──────┬───────────────▲──────┘
                        │ REST 接口      │ WebSocket 实时推送
                        ▼               │
                 ┌─────────────────────────────┐
                 │     Spring Boot 后端 (8080)  │
                 │ 登录鉴权 / 权限 / 业务 / 通知  │
                 └──────┬──────────┬────────────┘
                        │          │ 内部 HTTP（带登录态）
        ┌───────────────▼──┐   ┌───▼──────────────┐
        │  MySQL 8 (数据)   │   │  FastAPI AI (8001) │
        │  学生/课程/成绩/  │   │  LangGraph 智能体  │
        │  通知/审核/选课   │   │  向量+关键词检索    │
        └───────┬─────────┘   └─────────┬──────────┘
                │ 只读                  │ API
        ┌───────▼─────────┐   ┌───────────▼────────────┐
        │  Redis (缓存/限流)│   │ DeepSeek/SiliconFlow/Tavily │
        └─────────────────┘   └────────────────────────┘
```

**大白话理解**：
- **前端**（你看到的网页）→ 通过"接口"向后端**要数据**。
- **后端**（大脑）→ 验身份、查权限、算业务，然后读写 **MySQL**（数据仓库）。
- **Redis**（便利贴）→ 放"临时、要快的"东西：登录失败几次、每秒最多请求几次、选课页缓存。
- **实时通知** → 靠 **WebSocket**（对讲机）由后端**主动推**，而不是学生不停地刷新页面（打电话问）。
- **问 AI** → 前端→后端→独立的 **AI 服务**，AI 先"查真实数据 + 查课程资料"，**自由问答还会联网搜索**，再让大模型回答。

> 为什么要拆三层？就像餐厅分**前台（前端）、后厨（后端）、仓库（数据库）**：哪一环出问题都不影响其他环节，而且每一环都能单独升级。

### 5.2 技术架构分层（后端内部）

```
┌─ 表现层（Controller）─────── 接收请求、检查参数、返回统一格式 Result
│                             打个比方：前台接待，收单、核对、给回执
├─ 业务层（Service）────────── 业务规则、事务、权限校验、自动触发通知
│                             打个比方：后厨主管，按规矩做菜、管账目
├─ 数据访问层（Mapper）─────── 读写 MySQL（全参数化防 SQL 注入）
│                             打个比方：仓库管理员，扫码取货放货
├─ 基础设施层───────────────── MySQL(持久化) · Redis(限流/缓存) · WebSocket(推送)
│                             打个比方：水电气等公共设施
└─ 横切关注点───────────────── JwtInterceptor(验出入证) · RateLimitInterceptor(限流)
                               GlobalExceptionHandler(统一处理报错) · 配置类
```

> 这叫经典**三层架构**：每一层只管自己的事，只依赖下一层。想换某个零件（比如把 MyBatis-Plus 换成 JPA）只动对应的那一层，不影响别的。

### 5.3 一次请求的完整生命周期

以"教师保存成绩"为例：

```
前端点"保存"
 ① 带着 JWT（出入证）发请求 POST /api/grades/entry
 ② JwtInterceptor（门卫）：验出入证 → 看角色 → 查规则表（教师允许）→ 放行
 ③ Controller（前台）：检查参数合法（分数 0-100、学生属于这课）
 ④ Service（主管）：校验这门课确实是你教的 → 逐条更新成绩（事务）
 ⑤ Mapper（仓库）：写进 MySQL
 ⑥ 返回"成功"给前端
 ⑦ 前端刷新表格
```

> 每个请求都要过一遍"验身份 → 验权限 → 查参数 → 办业务 → 存数据"，这套流程就是后端的**安全网**。
> 打个比方：进公司大楼要刷卡（验身份）、刷完卡还看你能不能进这间办公室（验权限），然后才办公。

### 5.4 数据架构

**核心表（MySQL）—— 8 张表，就像 8 个分类档案柜**：

| 表 | 存什么 | 关键关联 |
|---|---|---|
| `staff` | 教职工（教秘 / 教师） | 角色、状态、`token_version`（出入证批次号） |
| `student` | 学生（学号、班级、专业、学分/GPA） | `token_version`（出入证批次号） |
| `course` | 课程（时间、地点、容量、授课教师、状态） | teacher_id → staff（**外键**：老师必须是真实存在的） |
| `student_course` | 选课 + 成绩明细（分数、标记 NORMAL/DEFER…） | student_id + course_id（**外键**，一个学生一门课只能选一次） |
| `course_grade_audit` | 成绩审核流（草稿→提交→审核通过→发布） | course_id → course（**外键**） |
| `oauth_binding` | GitHub 账号和系统账号的绑定关系 | provider_uid ↔ user_no（**唯一约束**：一个 GitHub 只能绑一个账号） |
| `notification` | 通知主表（标题、内容、类型、发送者） | — |
| `notification_receiver` | 通知接收明细（每人一条、已读标记） | notification_id + student_id（**外键**） |

> **外键是什么**：数据库层面的"编号核对"。比如选课记录里写的学号，数据库会强制核对"这个学号在学生表里必须存在"，不存在就拒绝写入。
> 大白话：就算程序写漏了检查，数据库也会帮你把关，**从根上杜绝"孤儿数据"**（查无此人的成绩、查无此课的通知）。

**Redis Key 设计（便利贴上记的事）**：

| Key | 记什么 | 多久过期 |
|---|---|---|
| `sms:login:fail:*` | 登录失败次数（≥5 次锁 5 分钟） | 5min |
| `sms:rate:login:user:*` | 单账号每分钟最多登录几次（限流） | 60s |
| `sms:rate:oauth:ip:*` | 授权码接口每 IP 限流 | 60s |
| `sms:oauth:state:*` | OAuth 的一次性暗号（防 CSRF） | 10min |
| `courseCenter::学生ID::筛选参数` | 选课中心缓存（30 秒一刷新） | 30s |

> MySQL 存"最终结果"（账本），Redis 存"临时状态"（便利贴），各司其职：账本不能丢，便利贴丢了也无所谓。

### 5.5 部署架构（东西怎么摆）

```
本机/服务器
 ├─ 前端   Vite 静态服务   :5173   （浏览器访问的页面）
 ├─ 后端   Spring Boot    :8080   （密钥全走环境变量，不写死在代码里）
 ├─ AI 服务 FastAPI       :8001   （端口由 AI_PORT 配置，只监听本机 127.0.0.1）
 └─ MySQL :3306 · Redis :6379     （数据 + 临时状态）
外部依赖：DeepSeek API（对话）· SiliconFlow API（向量/重排）· Tavily API（联网搜索）
```

> 安全要点：密码、密钥全用**环境变量**注入（就像开机输入密码，不贴在门上）；AI 服务只允许本机访问；跨域白名单可配置；接口文档默认关闭（不给外人看）。

### 5.6 关键设计决策（为什么这么设计——答辩高频考点）

| 决策 | 为什么 |
|---|---|
| 前后端分离 + 三层架构 | 职责清楚、可独立开发部署、零件可替换 |
| 成绩状态机（录入→提交→审核→发布） | 防篡改、责任可追溯、发布时自动通知 |
| 通知"先存库、后推送" | 消息不丢（离线补发），推送失败不影响业务 |
| 选课用行级锁 `FOR UPDATE` | 防并发超卖（见第六章） |
| 接口权限 fail-closed | 新接口忘了登记角色 = 直接 403（默认锁死），从机制上杜绝越权 |
| JWT 令牌版本吊销 | 改密码/禁用账号/改角色 → 旧出入证立即作废 |
| 未发布成绩遮蔽 | 成绩单只显示已发布成绩，草稿分数不外泄 |
| 数据库低权账号 + 外键 | 最小权限防提权；外键兜底数据一致 |
| 缓存反序列化白名单 | 防 Redis 被"投毒"后执行恶意代码 |
| WebSocket AUTH 首消息认证 | 令牌不进 URL，避免被日志记录泄露 |
| AI 独立服务 + RAG | 与主业务解耦；AI 基于真实数据回答，权限可控 |

## 六、核心业务流程（答辩必讲）

### 1. 选课流程（含并发安全）

```
学生点"选课" → 后端锁住这门课（SELECT...FOR UPDATE）
   → 检查：课发布了吗？满员了吗？重复选了吗？时间冲突吗？出成绩了吗？
   → 都通过 → 写入选课记录 + 选课人数+1 → 返回成功
```

**亮点（必讲）**：多个人同时抢最后一门课时，用**数据库行级锁**把同一门课的选课操作变成"排队一个一个来"，避免"大家都看到还剩 1 个名额、结果都选上了"的超卖问题。
> 打个比方：像演唱会抢票，系统锁住这张票，谁先抢到谁拿走，后面的人看到的就是"已售罄"。

### 2. 成绩发布流程（职责分离）

```
老师录入(草稿) → 提交(锁定) → 教秘审核(通过/退回) → 教秘发布 → 学生可见
      DRAFT         SUBMITTED      APPROVED           PUBLISHED
```

- 老师在**自己的**课程上录成绩（可 Excel 批量导入）；
- **提交后锁定**，不能再改（防篡改）；
- 教秘**审核通过**才能**发布**，发布后学生才看得到；
- 发布同时**自动重算学生学分和 GPA**：≥60 分（标记正常，缓考/缺考/舞弊不算）计入已修学分；GPA 按学分加权算；
- 发布同时**自动给选课学生推送"成绩已发布"通知**。

> 打个比方：老师写完卷子（草稿）→ 封卷提交（锁定）→ 教务检查（审核）→ 盖章公布（发布）。每一步都有人负责，出问题能追责。

### 3. 站内通知流程（WebSocket 实时推送）

```
老师/管理员 或 系统自动 → 先存进数据库
   → 存完，对"在线学生"通过 WebSocket（对讲机）推消息
   → 学生网页立刻弹未读角标
   → 不在线的学生 → 上线打开通知中心拉取历史（补发）
```

**三个自动触发点**：选课成功、成绩发布、课程调课（时间/地点被改）。

### 4. AI 问答流程

```
学生提问 → 后端验签转发 → AI 服务判断意图(查成绩/推荐课程/自由问答)
   → 查学业数据(成绩/课表) + 检索课程目录(向量+关键词→融合→重排)
   → 【自由问答】额外联网：Tavily 搜索网页资料（top3，含来源）
   → 把真实数据塞进提示词 → DeepSeek 生成回答（引用外部信息标注来源）
```

**亮点（必讲）**：AI 不是"瞎聊"，而是**先查这个学生的真实成绩和真实课程库，再回答**（这叫 RAG，检索增强生成），并且**只允许查自己的数据**；**自由问答还会通过 Tavily 联网搜索**补充外部资料并标注来源。
> 打个比方：AI 是个家教，先翻开"你的"成绩单和课表，再给你建议；遇到课表外的通用问题，还会先上网查资料再回答，并告诉你信息来自哪个网站，而不是凭感觉乱说。

## 七、项目亮点（"牛在哪"——答辩加分项）

> 每个亮点按 **做了什么 → 怎么实现 → 为什么重要** 讲。

### 亮点 1：WebSocket 实时站内通知
- **做了什么**：老师/管理员发通知，学生**在线秒收**；离线一上线就补发；有未读角标和通知中心。
- **怎么实现**：WebSocket（对讲机）+ 服务端"谁在线"登记表；通知**先存库再推送**（保证不丢）；前端断线自动重连 + 心跳保活。
- **为什么重要**：解决了"消息靠人传话、经常收不到"的痛点；比"每几秒刷新一次"省资源、更快。

### 亮点 2：通知系统的安全设计
- **做了什么**：老师只能发给**自己课程**的学生；学生只能标记**自己的**已读；令牌不放进 URL。
- **怎么实现**：JWT 用"连接后第一条 AUTH 消息"传递（避免进访问日志）；服务端强校验发送权限和已读归属；没登记的接口默认 403。
- **为什么重要**：功能再花哨，有权限漏洞也是白搭——这是安全工程思维。

### 亮点 3：高并发选课防超卖
- **怎么实现**：`SELECT ... FOR UPDATE` 行级锁，把"检查余量→选课→人数+1"变成原子操作。
- **为什么重要**：直接证明你懂**并发控制**，这是后端开发的核心能力。

### 亮点 4：安全加固体系（10+ 项）
- 密码 **BCrypt** 加密存储（单向绞肉，存的是肉馅不是原密码）；
- 登录失败 **锁定 + 限流**（Redis 计数，防暴力破解）；
- **JWT 令牌版本吊销**：用户表记 `token_version`，改密/禁用/改角色时 +1，旧令牌立即作废——就算令牌被偷，改密后也废了；
- **自助修改密码**：校验旧密码 + 强度（8-20 位含字母数字）；管理员可重置任意账号；
- 接口**角色权限拦截器**（fail-closed）：新接口忘登记角色 = 403，杜绝"忘了鉴权"；
- **未发布成绩遮蔽**：学生只看得到已发布成绩，草稿分数返回空；
- **数据库低权账号 `sms_app`**：只用一把"只开本库的钥匙"，不碰 root 权限（防注入/RCE 后提权）；
- **AI 请求体大小限制**（64KB，chunked 编码也拦）；
- **GitHub OAuth**：一次性 state 防 CSRF、防一码多用、唯一索引防重复绑定；
- 缓存**反序列化白名单**（防 Redis 被投毒执行恶意代码）；
- **数据库外键**兜底数据一致性；
- ECharts tooltip **HTML 转义**（防存储型 XSS）、500 异常带 **traceId**（像快递单号，不泄露内部细节却能定位）、登录失败提示统一文案（防撞库枚举账号）；
- SQL 全参数化（防 SQL 注入）。
- **为什么重要**：这不是"能跑就行"，而是认真考虑过**真实攻击面**，展示安全意识。

### 亮点 5：AI 智能助手（RAG + 智能体 + 联网搜索）
- **怎么实现**：独立 FastAPI 服务 + LangGraph 编排（判断意图→查资料→生成）；课程推荐用"提问重写 + 向量 + 关键词混合检索 + 重排"；**自由问答额外接入 Tavily 联网搜索**，外部资料（标题/链接/摘要，top3）作为补充上下文，回答标注来源。
- **为什么重要**：AI 不是玩具，落地到具体业务，还管住了数据权限；联网让 AI 能回答"系统之外"的通用问题，且不瞎编。

### 亮点 6：统计看板 & 数据口径
- 全校/教师成绩统计图表；**统计口径经过刻意设计**：全校分数段只统计**已发布**成绩（避免把草稿算进去）；教师端统计自己录入的全部成绩（实时反映）。
- **学分/GPA 口径统一**：学分只计入"已发布且 ≥60 分"的课；成绩单、仪表盘、GPA 全库对账零误差。
- **为什么重要**：做数据分析时"口径一致"是专业性的体现。

### 亮点 7：单元测试
- **66 个单元测试**（登录、改密、成绩、选课、通知、权限边界、AI 请求体过滤等），用 Mockito 模拟数据库，不碰真实库也能跑。
- **为什么重要**：展示工程质量意识——不是写完就完，而是"有测试兜底"。

## 十、常见答辩问题 Q&A（提前背熟）

**Q1：为什么用 WebSocket 而不是轮询？**
> 轮询是"前端每隔几秒问一次有没有新消息"（像每隔一会儿打一次电话问），浪费资源、有延迟；WebSocket 是"服务端有消息**主动推给你**"（像对讲机），实时又省资源。选它就是为了"学生一上线就能秒收通知"。

**Q2：WebSocket 认证怎么做？为什么不在 URL 里放 token？**
> URL 里的参数会被记进服务器/代理日志，令牌放里面等于泄露。所以先建立连接，客户端再发一条 AUTH 消息带上令牌，服务端校验通过才把会话加入可推送名单；校验失败直接关闭（4401）。

**Q3：怎么防止选课超卖？**
> 用数据库行级锁 `SELECT ... FOR UPDATE` 锁住课程记录，让"查余量 → 选课 → 人数+1"变成一气呵成（原子）的操作。多个请求并发时**排队执行**，不会都看到同一个剩余名额。

**Q4：AI 回答会不会乱编？**
> 用了 RAG（检索增强生成）：先把问题在真实课程库/成绩库里检索，把检索到的**真实数据**拼进提示词，再让大模型基于这些数据回答；并且检索和读取都做了权限控制，学生只能看到自己的数据。**资料查不到就说查不到，不硬编。**「自由问答」还会通过 Tavily 联网搜索外部资料，回答引用时标注来源。

**Q5：Redis 用在哪？**
> 三处：①登录失败计数与限流（防爆破）；②选课中心缓存（减少查库）；③共享状态。所有 Redis 操作在它故障时都会**降级放行**，不让缓存故障拖垮主流程。

**Q6：权限是怎么控制的？**
> 登录后签发 JWT 令牌（含角色）；后端拦截器对每个接口按"路径 + 角色"匹配规则，规则表里**没有的接口默认拒绝 403**（fail-closed，默认锁死）。新增接口必须登记角色，从机制上避免"忘了鉴权"。

**Q7：成绩流程为什么要"提交→审核→发布"？**
> 保证数据可信：提交后锁定防篡改；教秘审核把关；发布后才对学生可见，且发布时自动通知。职责分离，谁做了什么都有记录。

**Q8：项目有哪些测试？**
> **66 个单元测试**覆盖登录锁定、改密、成绩导入导出、选课、通知的权限边界、AI 请求体过滤等核心逻辑，用 Mockito 模拟数据库（不碰真实库），CI 可跑。
