# AI 学生信息管理系统 —— 项目解析与答辩指南

> 一份给"第一次看这个项目的人"讲清楚它是什么、怎么做的、牛在哪里的文档。
> 配套用途：毕业设计 / 课程设计答辩，或向老师 / 同学介绍项目。

---

## 一、一句话介绍

**这是一个给高校用的"一站式"教务系统**：学生选课、查成绩、问 AI 助手；老师录成绩、发通知；教务秘书管账号、审成绩、看统计。三者共用一套数据，配上**实时站内通知**和**AI 学业助手**，让教务工作线上化、智能化。

> 大白话：把"教务处 + 老师 + 学生"平时在线的 / 纸质的工作，搬到一个网页系统里，还能实时提醒、自动分析。

---

## 二、解决什么问题

| 现状痛点 | 本系统的解法 |
|---|---|
| 选课靠人工登记、容易超员、信息不透明 | 在线选课中心，容量实时显示、**并发安全**、时间冲突自动检测 |
| 成绩靠 Excel 传来传去、流程混乱 | 完整成绩流程：**录入 → 提交 → 审核 → 发布**，权限分明、可追溯 |
| 调课、成绩发布等消息传达靠口口相传 | **WebSocket 实时通知**：上线即收到，离线补发 |
| 学生不会解读成绩、不知道选什么课 | **AI 智能助手**：查成绩、做学业分析、推荐课程 |
| 数据分散、领导看不到全局 | 数据统计看板：专业分布、分数段、选课排行等图表 |

## 三、三种角色，各看各的

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│   学生 STUDENT │   │   教师 TEACHER │   │ 教秘 ADMIN   │
│  选课/查成绩   │   │  管课程/录成绩  │   │  管账号/审成绩 │
│  收通知/AI助手 │   │  发通知/看统计  │   │  发通知/看统计 │
└──────────────┘   └──────────────┘   └──────────────┘
         └──────────────┬──────────────┘
                 一套数据库 + 一套后端 + 一套前端
```

- **学生**：登录后选课、看课表、查成绩（只显示已发布）、收实时通知、问 AI。
- **教师**：创建/管理自己的课程，给课程录入成绩（支持 Excel 批量导入），给自己的学生发通知，看自己课程的成绩统计。
- **教秘（管理员）**：管所有账号、审核并发布成绩、监控选课、向任意学生发通知、看全校统计。

> 关键点：**每个人的权限都是被强制限制的**（后端逐接口校验），学生查不到别人的成绩、教师改不了别人的课程。

## 四、技术栈"大白话"解释

| 技术 | 是什么 | 在我们项目里干嘛 |
|---|---|---|
| **Vue 3 + TypeScript** | 前端框架 + 带类型检查的 JS | 写页面界面，类型安全减少 bug |
| **Element Plus** | 现成的漂亮 UI 组件库 | 表格、弹窗、表单、图表容器不用从零写 |
| **ECharts** | 图表库 | 统计页的各种柱状图、饼图 |

| **MyBatis-Plus** | 数据库操作框架 | 不用手写大量 SQL，用对象方式查库 |
| **MySQL 8** | 关系型数据库 | 存学生、课程、成绩、通知等所有核心数据 |
| **Redis** | 内存数据库 | 登录防爆破计数、限流、选课中心缓存、WebSocket 会话表 |
| **WebSocket** | 全双工长连接 | **服务端主动推消息**给学生（这是通知"实时"的关键） |
| **FastAPI + LangGraph** | Python 后端 + AI 编排框架 | 独立的 AI 服务：意图识别 → 检索 → 生成回答 |
| **DeepSeek API** | 大语言模型 | AI 对话生成 |
| **ChromaDB + BM25** | 向量库 + 关键词检索 | 课程目录"混合检索"，让 AI 基于真实数据回答 |
| **JWT + BCrypt** | 登录令牌 + 密码加密 | 登录后发令牌，密码用不可逆哈希存库 |
| **EasyExcel** | Excel 读写库 | 成绩/账号的批量导入导出 |

## 五、架构分析（答辩深度讲解）

### 5.1 系统总览图

```
                 ┌─────────────────────────────┐
                 │       前端 Vue3 (5173)       │
                 │ 页面 + 图表 + WebSocket 客户端 │
                 └──────┬───────────────▲──────┘
                        │ REST 接口      │ WebSocket 实时推送
                        ▼               │
                 ┌─────────────────────────────┐
                 │     Spring Boot 后端 (8080)  │
                 │ 登录鉴权 / 权限 / 业务 / 通知  │
                 └──────┬──────────┬────────────┘
                        │          │ 内部 HTTP（带登录态）
        ┌───────────────▼──┐   ┌───▼──────────────┐
        │  MySQL 8 (数据)   │   │  FastAPI AI (8001) │
        │  学生/课程/成绩/  │   │  LangGraph 智能体  │
        │  通知/审核/选课   │   │  向量+关键词检索    │
        └───────┬─────────┘   └─────────┬──────────┘
                │ 只读                  │ API
        ┌───────▼─────────┐   ┌─────────▼──────────┐
        │  Redis (缓存/限流)│   │  DeepSeek/SiliconFlow │
        └─────────────────┘   └────────────────────┘
```

**简单理解**：
- 浏览器（前端）通过 **HTTP 接口** 向后端要数据；
- 后端是"大脑"，负责校验身份、判断权限、处理业务，然后读写 **MySQL**；
- 高频率、需要共享的状态（登录失败次数、限流计数、选课缓存）放 **Redis**，读写快；
- 学生在线的实时通知，通过 **WebSocket 长连接**由后端主动"推"过去，而不是学生不断刷新；
- 学生问 AI，前端把请求给后端，后端转发给独立的 **AI 服务**，AI 服务先"查数据库 + 检索课程资料"，再调用大模型生成回答。

> 三层分离的好处：前端只管展示、后端只管业务、AI 独立部署。哪层出问题都不影响其他层。

### 5.2 技术架构分层（后端内部）

```
┌─ 表现层（Controller）─────── 接收 HTTP 请求、参数校验、返回统一 Result{code,message,data}
│
├─ 业务层（Service）────────── 业务规则、事务管理、权限校验、自动通知触发
│
├─ 数据访问层（Mapper）─────── MyBatis-Plus 封装 SQL，读写 MySQL（全参数化防注入）
│
├─ 基础设施层───────────────── MySQL(持久化) · Redis(限流/锁定/缓存/会话) · WebSocket(推送)
│
└─ 横切关注点───────────────── JwtInterceptor(鉴权) · RateLimitInterceptor(限流)
                               GlobalExceptionHandler(统一异常) · 配置类
```

> 经典**三层架构** + 拦截器/切面：每一层职责单一、只依赖下一层，替换某一层不影响其他层（例如把 MyBatis-Plus 换成 JPA 只动 Mapper 层）。

### 5.3 一次请求的完整生命周期

以"教师保存成绩"为例：

```
前端点"保存"
 ① POST /api/grades/entry 带 JWT
 ② JwtInterceptor：验 JWT → 取角色 → 匹配路径规则(教师) → 写入 UserContext
 ③ Controller：@Valid 校验(成绩 0-100、学生属于该课程)
 ④ Service：校验课程归属当前教师 → 逐条更新成绩(事务)
 ⑤ Mapper：参数化 SQL 写 MySQL
 ⑥ 返回 Result{code:200}
 ⑦ 前端更新表格
```

> 每个请求都过一遍"鉴权 → 权限 → 校验 → 业务 → 数据"，这套链路就是后端的"安全网"。

### 5.4 数据架构

**核心表（MySQL）**：

| 表 | 作用 | 关键关联 |
|---|---|---|
| `staff` | 教职工（教学秘书 ADMIN / 教师 TEACHER） | 角色、状态、院系 |
| `student` | 学生（学号、班级、专业、学分/GPA 汇总） | — |
| `course` | 课程（时间、地点、容量、授课教师、状态） | teacher_id → staff |
| `student_course` | 选课 + 成绩明细（分数、标记 NORMAL/DEFER…） | student_id + course_id |
| `course_grade_audit` | 成绩审核流（DRAFT→SUBMITTED→APPROVED→PUBLISHED） | course_id |
| `oauth_binding` | GitHub OAuth 绑定关系 | provider_uid ↔ user_no |
| `notification` | 通知主表（标题、内容、类型、发送者） | — |
| `notification_receiver` | 通知接收明细（每人一条、已读标记） | notification_id + student_id |

**Redis Key 设计**：

| Key | 用途 | 过期 |
|---|---|---|
| `sms:login:fail:*` | 登录失败计数（≥5 锁定 5 分钟） | 5min |
| `sms:rate:login:user:*` | 单账号每分钟登录限流 | 60s |
| `sms:rate:oauth:ip:*` | 授权码接口每 IP 限流 | 60s |
| `sms:oauth:state:*` | OAuth state 一次性校验（防 CSRF） | 10min |
| `courseCenter::学生ID::筛选参数` | 选课中心缓存（TTL 30s 保证新鲜度） | 30s |

> 数据库存"最终结果"，Redis 存"临时状态 + 高频读缓存"，各司其职。

### 5.5 部署架构

```
本机/服务器
 ├─ 前端   Vite 静态服务   :5173
 ├─ 后端   Spring Boot    :8080  （密钥全走环境变量，不入库/不入代码）
 ├─ AI 服务 FastAPI       :8000  （仅监听 127.0.0.1，本机访问）
 └─ MySQL :3306 · Redis :6379
外部依赖：DeepSeek API（对话）· SiliconFlow API（向量/重排）
```

> 部署要点：密钥环境变量注入；AI 服务只监听本机 + 独立 JWT 验签；跨域白名单配置化；接口文档（Swagger/Knife4j）生产默认关闭。

### 5.6 关键设计决策（为什么这么设计）

| 决策 | 原因 |
|---|---|
| 前后端分离 + 三层架构 | 职责单一、可独立开发部署、可替换实现 |
| 成绩状态机（录入→提交→审核→发布） | 数据可信、防篡改、责任可追溯，发布时自动通知 |
| 通知"先落库、后推送" | 保证消息不丢（离线补发），推送失败不影响业务 |
| 选课用行级锁 `FOR UPDATE` | 防并发超卖 |
| 接口权限 fail-closed | 新接口忘登记角色 = 403，从机制上杜绝越权 |
| 缓存反序列化白名单 | 防 Redis 投毒 → 反序列化执行恶意代码（RCE） |
| WebSocket AUTH 首消息认证 | 令牌不进 URL，避免日志泄露 |
| AI 独立服务 + RAG | 与主业务解耦；基于真实数据回答，且数据权限可控 |

## 六、核心业务流程（答辩必讲）

### 1. 选课流程（含并发安全）

```
学生点"选课" → 后端锁住该课程行(SELECT...FOR UPDATE)
   → 校验：课程已发布？没满员？没重复选？时间不冲突？成绩没发布？
   → 通过则插入选课记录 + 选课人数+1 → 返回成功
```

**亮点**：多个人同时抢最后一门课时，用**数据库行级锁**把同一课程的选课操作串行化，避免"都看到还剩 1 个名额、都选上了"的超卖问题。这是高并发下最常见的坑。

### 2. 成绩发布流程（职责分离）

```
教师录入(草稿) → 提交(锁定) → 教秘审核(通过/退回) → 教秘发布 → 学生可见
      DRAFT         SUBMITTED      APPROVED           PUBLISHED
```

- 教师在**自己的**课程上录成绩（可 Excel 批量导入）；
- 提交后成绩**锁定**，不能再改（防篡改）；
- 教秘审核通过后才能**发布**，发布后学生才能在成绩单里看到；
- **发布的同时重算学生学分与 GPA**：该课程成绩 ≥60 分（标记 NORMAL，缓考/缺考/舞弊不算）计入已修学分；GPA 按学分加权（Σ(单科绩点×学分)÷总学分，绩点 ≥90→4.0 / ≥80→3.0 / ≥70→2.0 / ≥60→1.0）；
- 发布的同时**自动给该课程选课学生推送"成绩已发布"通知**。

### 3. 站内通知流程（WebSocket 实时推送）

```
老师/管理员 或 系统自动 → 写数据库(notification + 接收人明细)
   → 事务提交后，对"在线学生"通过 WebSocket 推 JSON
   → 学生前端收到 → 未读角标 +1、列表顶部插入
   → 离线学生上线 → 打开通知中心拉取历史（补发）
```

**三个自动触发点**：选课成功、成绩发布、课程调课（时间/地点被改）。

### 4. AI 问答流程

```
学生提问 → 后端验签转发 → AI服务做意图识别(查成绩/推荐课程/自由问答)
   → 需要时"检索"：把问题改写后，向量检索 + 关键词检索 → 融合 → 重排
   → 把真实数据(成绩/课程目录)塞进提示词 → DeepSeek 生成回答
```

**亮点**：AI 不是"瞎聊"，而是**基于这个学生的真实成绩和真实课程库**回答（RAG 检索增强生成），并且只允许查自己（数据权限在服务端强制）。

## 七、项目亮点（"牛在哪"）

> 答辩时这部分是加分项。每个亮点：**做了什么 → 怎么实现 → 为什么重要**。

### 亮点 1：WebSocket 实时站内通知
- **做了什么**：老师/管理员发通知，学生**在线立即收到**；离线上线补发；带未读角标和通知中心。
- **怎么实现**：原生 WebSocket + 服务端会话注册表（学生ID → 在线连接）；通知先落库（保证不丢），事务提交后推送给在线学生；前端断线指数退避自动重连 + 心跳保活。
- **为什么重要**：解决了"消息传达靠口口相传"的痛点；WebSocket 单向推送比轮询省资源、延迟低。

### 亮点 2：通知系统的安全设计
- **做了什么**：教师只能发给自己课程的学生；学生只能标记自己的已读；WebSocket 认证不在 URL 里放令牌。
- **怎么实现**：JWT 经连接后**首条 AUTH 消息**传递（避免令牌进访问日志）；服务端强校验发送权限与已读属主；接口层 fail-closed 角色规则（没登记的接口默认 403）。
- **为什么重要**：有权限漏洞的系统再花哨也是不安全的，这是安全工程思维。

### 亮点 3：高并发选课防超卖
- **怎么实现**：`SELECT ... FOR UPDATE` 行级锁串行化同课程的容量检查与更新。
- **为什么重要**：直接展示了你懂并发控制，是后端开发的核心能力。

### 亮点 4：安全加固体系
- 密码 **BCrypt** 哈希存储；登录失败**锁定 + 限流**（Redis 计数，防爆破）；
- 接口**角色权限拦截器**（fail-closed）：新接口忘登记角色 = 直接 403，杜绝"忘了鉴权"；
- **GitHub OAuth** 登录（一次性 state 防 CSRF、绑定防一码多用）；
- 缓存序列化**反序列化白名单**（防 Redis 被投毒后执行恶意代码）；
- 数据库 SQL 全参数化（防 SQL 注入）。
- **为什么重要**：这不是"能跑就行"，而是考虑了真实攻击面，展示安全意识。

### 亮点 5：AI 智能助手（RAG + 智能体）
- **怎么实现**：独立 FastAPI 服务 + LangGraph 编排（意图识别→检索→生成）；课程推荐用"提问重写 + 向量 + BM25 混合检索 + 重排"。
- **为什么重要**：AI 落地到具体业务场景，且数据权限安全。

### 亮点 6：统计看板 & 数据口径
- 全校/教师成绩统计图表；**统计口径经过刻意设计**（全校分数段只统计已发布成绩，避免把草稿成绩算进去；教师端统计自己录入的全部成绩，录入即实时反映）。
- **学分/GPA 口径统一**：学分只计入"已发布且 ≥60 分"的课程；学生成绩单展示**单科绩点**与**平均学分绩（GPA）**，与仪表盘口径完全一致（发布时重算，全库对账零误差）。
- **为什么重要**：做数据分析时"口径一致"是专业性的体现。

### 亮点 7：单元测试
- 52 个单元测试（登录、成绩、选课、通知、权限边界等），Mockito 隔离数据库跑测试。
- **为什么重要**：展示工程质量意识。

### 8.2 后端 backend —— 分层与文件作用

```
backend/src/main/java/com/example/sms/
├── controller/    # 接口层：接收 HTTP 请求 → 调用 Service → 返回 Result
├── service/       # 业务层：业务规则 + 事务 + 权限 + 自动通知
├── mapper/        # 数据访问层：读写 MySQL（MyBatis-Plus）
├── config/        # 配置与横切：鉴权/限流/Redis/WebSocket/CORS/初始化
├── websocket/     # WebSocket 通知：会话注册表 + 消息处理器
├── entity/        # 数据库实体（一张表对应一个类）
├── dto/ vo/       # 请求体对象 / 返回给前端的数据对象
├── util/          # 工具：JWT 签发解析、当前登录用户上下文
├── common/        # 统一响应 Result、业务异常、全局异常处理
└── excel/         # Excel 导入导出行模型
```

**各层关键文件作用**：

| 文件 | 作用 |
|---|---|
| `AuthController` / `AuthService` | 登录/签发 JWT；登录失败锁定、限流、OAuth 复用 |
| `AccountController` / `AccountService` | 学生/教职工账号管理（增删改、Excel 导入导出、重置密码、冻结） |
| `CourseController` / `CourseService` | 课程 CRUD、发布、**调课（已发布仅改时间/地点 + 自动通知）** |
| `GradeController` / `GradeService` | 成绩录入/导入/提交/审核/发布/查询；发布时自动通知选课学生 |
| `EnrollController` / `EnrollService` | 选课/退课（行级锁防超卖、时间冲突检测）、代选、监控 |
| `StatsController` / `StatsService` / `StatsMapper` | 全校/教师统计（原生 SQL 聚合，只统计已发布成绩） |

| `NotificationController` / `NotificationService` | 通知发送（手动/系统）、收件箱、未读数、已读、发件箱；事务提交后 WebSocket 推送 |

| `WebConfig` | 注册拦截器路径、排除登录/文档路径 |
| `RedisConfig` | Redis 缓存（TTL 30s + **反序列化白名单**）、原子 Lua 脚本（INCR+EXPIRE） |
| `WebSocketConfig` | 注册 `/ws/notifications` 端点、**会话空闲超时 60s** |
| `WsSessionRegistry` | 学生ID → 在线连接 的会话表（多标签页支持、失效清理） |
| `NotificationWebSocketHandler` | WS 消息处理：**首条 AUTH 消息验 JWT**、心跳 PONG、未认证超时关闭 |
| `DataInitializer` | 启动时确保初始账号存在（admin/T1001/S20230001…，不覆盖改过的密码） |
| `MybatisPlusConfig` | 分页插件配置 |
| `CorsConfig` / `Knife4jConfig` | 跨域白名单（配置外置）/ 接口文档开关（生产默认关） |
| `JwtUtil` | JWT 生成/解析（HS256，密钥强制环境变量） |
| `UserContext` | ThreadLocal 存"当前登录用户"，请求内全局可读 |
| `GlobalExceptionHandler` | 统一异常 → 统一 JSON（业务 400、越权 403、兜底 500） |
| `Result` / `BusinessException` | 统一响应包装 / 带状态码的业务异常 |

> 答辩要点：只要说出"接口层→业务层→数据层 + 拦截器做鉴权"的分层，评委就知道你懂架构。

## 十、常见答辩问题 Q&A（提前背熟）

**Q1：为什么用 WebSocket 而不是轮询？**
> 轮询是"前端每隔几秒问一次有没有新消息"，浪费资源、有延迟；WebSocket 是"服务端有消息主动推给你"，实时且省资源。选它就是为了"学生一上线就能实时收到"。

**Q2：WebSocket 认证怎么做？为什么不在 URL 里放 token？**
> URL 里的参数会被记进服务器/代理日志，token 放里面等于泄露。所以先建立连接，客户端再发一条 AUTH 消息带上 JWT，服务端校验通过才把会话加入可推送名单；校验失败直接关闭（4401）。

**Q3：怎么防止选课超卖？**
> 用数据库行级锁 `SELECT ... FOR UPDATE` 锁住课程记录，让"检查余量 → 插入选课 → 人数+1"原子化。多个请求并发时排队执行，不会都看到同一个剩余名额。

**Q4：AI 回答会不会乱编？**
> 用了 RAG 检索增强：先把问题在真实课程库/成绩库里检索，把检索到的真实数据拼进提示词，再让大模型基于这些数据回答；并且检索和读取都做了权限控制，学生只能看到自己的数据。

**Q5：Redis 用在哪？**
> 三处：①登录失败计数与限流（防爆破，多实例共享）；②选课中心缓存（减少查库）；③未来多实例时的共享状态。所有 Redis 操作在它故障时都会"降级放行"，不让缓存故障拖垮主流程。

**Q6：权限是怎么控制的？**
> 登录签发 JWT 令牌（含角色）；后端拦截器对每个接口按"路径 + 角色"匹配规则，规则表里没有的接口**默认拒绝 403**（fail-closed）。新增接口必须登记角色，从机制上避免"忘了鉴权"。

**Q7：成绩流程为什么要"提交→审核→发布"？**
> 保证数据可信：提交后锁定防篡改；教秘审核把关；发布后才对学生可见，且发布时触发通知。职责分离，谁做了什么都有记录。

**Q8：项目有哪些测试？**
> 52 个单元测试覆盖登录锁定、成绩导入导出、选课、通知的权限边界等核心逻辑，用 Mockito 模拟数据库，CI 可跑。
